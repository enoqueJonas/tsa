## Latest System Thinker-only remediation: lost HTTP response after durable commit

A new focused lesson **Ambiguous HTTP Outcomes and Idempotent Retries** was inserted into **Data Flow and Integration immediately after Failure Across Integrations**, before the synthesis lab. Its complete Python 3 standard-library code in `system-thinker-http-ambiguous-commit-worked.ts` runs an actual loopback HTTP server and a temporary durable SQLite database, deliberately cuts the first connection **after SQL commit and before HTTP response**, then restarts the listener and replays an operation with the original quoted idempotency key. Wrong payload with the same key returns 409; wrong Team returns 403 before replay; a second new transition is rejected; final durable side-effect count remains exactly one.

The learner code itself is extracted and executed by `scripts/check-system-thinker-http-ambiguous-commit.mjs`, registered in the curriculum test suite. This test **passed** in the `validate` job of run [#41444433658](https://github.com/enoqueJonas/tsa/actions/runs/41444433658) before the broader workflow was superseded by later commits. This proves the bounded network/SQLite experiment, **not** the real Builder Django/Steward API authentication, concurrent same-key calls, remote notifications, distributed atomicity or enterprise deployment.

Research anchors: [IETF HTTPAPI draft-08 (published 2026-10-22)](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header), [AWS Builders' Library retries and idempotency](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/), and [RFC 9110 HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110).
