This learner example actually:

- Publishes a full-state v8 `retired` event **before** v7 `production`, then a duplicate v8. PostgreSQL `ON CONFLICT ... WHERE excluded.version > projection.version` prevents regression, while the `processed(event_id)` record and the local projection/effect are written atomically. This is deliberate **producer-originated business-version inversion**, not fabricated RabbitMQ FIFO reordering.
- Configures a durable work queue with a dead-letter exchange, quarantine queue and explicit binding. Its initial consumer rejects unsupported `schema_version=2` with `basic_nack(requeue=False)`, and the quarantine delivery's `x-death` header records the original queue and reason `rejected`.
- Simulates a consumer **adapter capability upgrade**, then republishes the *unchanged original bytes and stable event ID* with broker publisher confirms. It acknowledges the quarantined delivery **only after** confirmation. The resumed handler creates one local effect; deliberate duplicate replay creates no second effect.
- Proves the final v8 projection and reports two applied local effects across three distinct processed event IDs. The test runs the **exact learner-published Python** against services rather than executing an invented mock.

Added a separate **Lab 3: RabbitMQ Poison-Message Quarantine, Replay and Ordering** (three activities) in learner sequence after the RabbitMQ delivery/ack lab and before transactional outbox.
